# 건기식 원료 지식그래프 — 설계 패키지

LLM 건강 코치가 건강기능식품 원료를 추천하거나 설명할 때 근거로 쓰는 Neo4j 그래프의 설계와 검증 코드다. 이 폴더 전체를 코딩 에이전트에 올려서 이해하고 확인하는 용도로 만들었다.

## 에이전트에게 맡길 때

이 폴더를 첨부하고 아래처럼 요청하면 된다.

> `supplement-graph/README.md`부터 읽고 설계를 요약해 줘. 그다음 `python3 test/run_tests.py`를 돌려서 문서에 적힌 동작이 실제로 맞는지 확인해 줘.

에이전트가 지켜야 할 규칙은 이 문서의 "바꾸면 안 되는 규칙"에 있다. 설계를 바꾸는 제안은 이 규칙과 [`docs/DESIGN.md`](docs/DESIGN.md) 7장의 미확정 항목을 기준으로 판단한다.

## 한눈에 보기

```
원천: 식약처 API · 크롤링 · 기획 시트
  → 원본 저장(RDB) → 정규화·검수 → Neo4j
  → 서버가 정해진 쿼리로 조회 → 안전 필터 → 근거 묶음 → LLM 답변
```

- **원료가 중심이다.** 증상 → 기전 → 기능성 ← 원료 경로로 "왜 이 원료인지" 설명한다.
- **원료 유형은 보조 라벨이다.** `(:Ingredient:Nutrient)`, `(:Ingredient:Notice)`, `(:Ingredient:Individual)`. 영양성분, 고시형, 개별인정형이다.
- **같은 물질은 `Substance`로 묶는다.** 업체별 인정번호, 고시형 전환, 사용자 표현 차이("오메가3")를 해결한다.
- **약물은 성분 → 계열 2단계다.** 처방은 성분으로 들어오고 원료 주의사항은 "항응고제" 같은 계열로 쓰여 있어서 `IN_CLASS`로 잇는다.
- **개별인정형만 API로 계속 바뀐다.** 동기화는 API가 소유한 필드만 고치고, 사람이 검수한 관계는 건드리지 않는다.

## 바꾸면 안 되는 규칙

1. **LLM은 Cypher를 직접 쓰지 않는다.** 서버가 `cypher/30_queries.cypher`의 쿼리를 정해진 순서로 실행하고, LLM은 결과만 받는다.
2. **추천 전에는 반드시 `safety_filter`를 통과시킨다.** `allowed = false`인 원료는 빼거나 "전문가 상담" 문구를 강제한다.
3. **섭취량 같은 수치는 노드 속성값을 그대로 인용한다.** LLM이 숫자를 만들지 않게 한다.
4. **조회는 항상 `status = 'active'` 원료만 쓴다.** `needs_review` 기능성 관계는 추천 경로에서 뺀다. 안전 관계는 항상 적용한다.
5. **동기화는 API 소유 필드만 덮어쓴다.** `SET i += row.api`는 쓰고, `SET i = {...}`나 관계 삭제는 쓰지 않는다.
6. **API에서 빠진 원료는 지우지 않는다.** `missing_since`만 표시하고 사람이 확인한 뒤 `revoke_individual`로 처리한다.
7. **개인 데이터(검진, 설문, 처방)는 그래프에 넣지 않는다.** 그래프는 공유 지식만 담는다. 개인 데이터는 쿼리 파라미터로만 넘긴다.
8. **매칭이 불확실하면 추천하지 않고 되묻는다.**

## Cypher 파일

| 파일 | 내용 | 실행 방식 |
|---|---|---|
| `cypher/01_schema.cypher` | 제약조건, 일반·전문검색(cjk)·벡터 인덱스 | 그대로 실행. 여러 번 실행해도 안전 |
| `cypher/02_seed_sample.cypher` | 엑셀 내용으로 만든 테스트 데이터 | 그대로 실행 (테스트용) |
| `cypher/10_load.cypher` | 시트·고시형 적재 템플릿 | 서버가 `$rows`를 넘겨 블록별 실행 |
| `cypher/20_sync_individual.cypher` | 개별인정형 동기화, 검수, 취소, 고시형 전환 | 서버가 블록별 실행 |
| `cypher/30_queries.cypher` | 서비스 조회 (증상 매칭 → 탐색 → 안전 필터 → 근거) | 서버가 블록별 실행 |

파라미터가 있는 파일은 블록 단위로 쓴다. 각 블록은 `// @query 이름`으로 시작하고 `;`로 끝난다. 블록 위 주석에 파라미터 형태가 적혀 있다. 테스트 스크립트도 이 표시로 블록을 찾는다.

## 검증 방법

Docker가 필요하다. 처음 실행하면 `neo4j:5.26-community` 이미지(약 600MB)를 받는다.

```bash
cd supplement-graph
python3 test/run_tests.py          # 임시 Neo4j를 띄워 검증하고 정리
python3 test/run_tests.py --keep   # 끝나도 유지 → http://localhost:7474 (인증 없음)에서 직접 조회
```

테스트가 확인하는 동작은 다음과 같다.

- 스키마 반복 적용, 한글 전문검색, 물질 별칭 검색
- 증상 → 원료 설명 경로, 조건 → 원료, 약물 고갈 영양소
- 안전 필터: 약 성분 → 계열 경유 차단, 임산부 조건 차단
- 개별인정형 동기화: 신규 생성, 해시 동일 시 무변경, 원문 변경 시 검수 표시 및 사람 관계 유지, 검수 전 추천 제외와 검수 후 복귀
- 전체 수집 누락 표시와 재등장 시 해제, 취소, 고시형 전환

2026-11-10에 Neo4j 5.26 Community에서 26개 항목이 모두 통과했다.

아직 테스트하지 않은 블록이 있다. `symptom_vector`, `products_for_ingredient`, `set_ingredient_embedding`, `cleanup_sheet_edges`, `upsert_company_recognition`, 그리고 `10_load.cypher`의 `upsert_symptom`·`upsert_condition`·`upsert_drug`·`upsert_function_tag`·`upsert_mechanism`·`link_*` 템플릿이다. 이 중 적재에 쓰는 블록은 시나리오 테스트는 없지만 `load/build_graph.py`가 실데이터로 실행한다(아래 "실데이터 적재").

## 실데이터 적재

통합 엑셀(`../data/건기식원료_통합_영양성분_고시형_개별인정형_261110.xlsx`)을 `supplement-graph-neo4j` 컨테이너에 올린다. 브라우저는 http://localhost:7476, Bolt는 `localhost:7689`이고 비밀번호는 `.neo4j.env`에 있다. `openpyxl`이 필요하다.

```bash
docker compose --env-file .neo4j.env up -d
python3 load/build_graph.py                 # 적재 후 엑셀과 대조
python3 load/build_graph.py --verify-only   # 대조만
```

| 엑셀 시트 | 그래프 |
|---|---|
| 통합(기준) | `Ingredient` 538개 (영양성분 28, 고시형 68, 개별인정형 442). 같은 인정번호는 API 행을 쓰고, 크롤링 행의 업체는 `HOLDS_RECOGNITION`으로 붙인다 |
| 기능성 태그, 기전, 증상 | `FunctionTag` 28, `Mechanism` 59, `Symptom` 69. 엑셀에서 삭제로 표시된 기전 2개는 넣지 않는다 |
| 경로 | `HAS_FUNCTION`, `SUPPORTED_BY`, `EXPLAINED_BY`, `REPLENISHED_BY`. 근거 열(출처 기관, 문서, URL, 원문, 판정)을 관계 속성으로 남긴다 |
| 통합(기준)의 주의사항 문구 | `EXCLUDES`, `INTERACTS_WITH`. 아래 주의 참고 |

적재 스크립트는 엑셀의 "연결" 경로와 그래프를 탐색해 나온 경로를 원료별로 비교한다. 2026-11-10 적재에서 8,545개 경로가 모두 일치했다.

적재 결과를 쓸 때 알아야 할 점은 다음과 같다.

- **안전 관계는 키워드로 뽑은 것이다.** 엑셀에는 조건·약물 시트가 없어서 주의사항 문구에서 대상군 5개(`POP-*`)와 약물 계열 8개(`CLS-*`)를 정규식으로 찾았다. 관계에 `derived = true`, `evidence = 'hypothesis'`, 원문 절(`reason`, `note`)을 남겼다. 사람이 검수하기 전까지는 누락과 오탐이 있을 수 있다. 질환 조건(`DIS-*`)은 질환을 가진 사람을 가리키는 절만 뽑는다: 당뇨병, 고혈압, 신장, 간, 위장관, 심장·심혈관, 고지혈증·고콜레스테롤혈증, 갑상선 질환 8개. 사용자의 관리질환·동반질환은 `pipeline.DISEASE_KEYWORDS`로 이 코드에 대응시켜 안전 검증에만 쓰고, 추천 근거로는 쓰지 않는다. "당뇨 전단계"·"고혈압 전단계"도 당뇨·고혈압 코드에 걸린다. 통풍·골다공증·관절염·안구건조증은 주의사항 원문에 해당 문구가 없어 규칙이 없다. 규칙만 바꿨을 때는 `python3 load/build_graph.py --safety-only`로 안전 관계만 다시 만든다.
- **약물은 계열만 있다.** 성분 단위 `Drug`와 `IN_CLASS`가 없으므로 서버가 처방을 계열 ID로 바꿔 넘겨야 한다. 복용 약이 하나라도 있으면 `CLS-any`를 함께 넘긴다.
- **섭취량 수치는 API 출처 개별인정형에만 있다.** 영양성분·고시형·크롤링 출처는 문구가 기능성별로 갈려 있어 숫자로 파싱하지 않고 `intake_raw` 원문만 둔다. `evidence_pack`이 `intake_raw`를 함께 돌려준다.
- **모든 원료가 `review_state = 'unreviewed'`다.** 엑셀의 태그 매칭은 사람 검수 여부를 알 수 없어서 검수 완료로 표시하지 않았다. 추천 경로는 관계의 `needs_review`만 보므로 조회에는 영향이 없다.
- **`Substance`, `Product`, 조건별 `RECOMMENDS`는 없다.** 이 엑셀에 해당 데이터가 없다.

## 추천 파이프라인

`reco/`가 사용자 데이터 한 건을 받아 추천 3개, 진료 권고, 또는 둘 다를 낸다. 맥락 데이터(생애주기, 관심사, 시너지)는 `load/build_context.py`가, 복용약 → 영양소 근거는 `load/build_drugs.py`가 올린다.

```bash
python3 load/build_context.py   # build_graph.py 다음에 한 번
python3 load/build_drugs.py     # 복용약 → 영양소 (load/refs/drug_nutrient_kr.json)
python3 -m reco                 # ../data/sample_patients*.json → out/recommendations.{json,md}
```

TOP-10과 선정 3개에는 영양제 탭용 `detail`(일일섭취량 `daily_intake`, 원재료명 `raw_material`, 섭취 시 주의사항 `precautions`, 주된 기능성 `main_function`)이 붙는다. 전부 그래프에 있는 식약처 원문이고 LLM이 쓰지 않는다. 원본에 없는 값은 `null`이다. 개별인정형은 원재료 자료가 없어 인정 원료명을 쓰고 `raw_material_basis`에 그 사실을 적는다.

점수제는 `python3 test/test_scoring.py`로 확인한다(그래프·LLM 없이 8건). 정규화 프롬프트를 고치면 `python3 test/eval_normalize.py`로 확인한다(짧은 구 주호소 20건 + 샘플 13명의 진료 판정, LLM 호출 과금). 기대값은 `test/normalize_cases.json`에 있고 약사 검토를 거친 값이 아니다.

| 단계 | 하는 일 | 구현 |
|---|---|---|
| 1 | 주호소(약사가 적은 짧은 구)를 증상 노드로 정규화하고 응급·진료 필요를 판정한다. `emergency`는 "진료 요망", `visit`은 "진료 권고"를 먼저 낸다. 둘 다 사유 증상과 그 증상에 걸리는 원료를 뺀 나머지로 추천을 이어간다(추천은 참고용 제안이다) | LLM (`reco/llm.py`, reasoning low), `pipeline.normalize` |
| 2-1 | 사용자 증상 → 기전 → 기능성 → 원료. 그 나이·성별의 생애주기 증상과 겹치는 증상을 표시한다 | `symptom_candidates`, `lifestage_symptoms` |
| 2-2 | 나이·성별 → 세그먼트 → 관심사 → 원료 | `interest_candidates` |
| 2-3 | 복용약 → 영양소. 사용자 약 이름·분류에 그래프의 정규식(`Drug.match`)을 걸어 약 성분·계열을 알아내고 `DEPLETES`를 따라간다. A 등급만 후보가 되고 B 등급은 참고 표시로 붙는다 | `drug_matchers`, `drug_candidates` |
| 3 | 같은 원료를 하나로 합친다. 순서는 직접 경로로 덮는 사용자 증상 수가 가장 먼저다. 이때 기전 하나로 설명되는 증상들은 하나로 센다(증상-기전 최대 짝짓기, `pipeline.independent_symptoms`. 예: 갱년기·생리주기·예민함이 '여성호르몬 변화' 하나로만 이어지면 1). 그 수가 같으면 점수(증상·복용약·관심사 기준마다 1점, 생애주기 우선 증상 가점 1점, 최대 4점), 증상 > 복용약 > 관심사 기준이 있는 쪽, 생애주기 우선 증상을 직접 덮는 수, 덮는 증상 수, 생애주기 증상 수, 근거 확정 수 순(`pipeline.rank_key`) | `pipeline.combine` |
| 4-1 | `safety_filter`에서 강도가 `avoid`인 원료를 뺀다 | `pipeline.verify` |
| 4-2 | `caution` 문구를 후보에 붙이고, 시너지 짝과 길항 쌍을 찾는다 | `synergy_partners`, `antagonist_pairs` |
| 4-3 | 경로의 모든 구간에 국내 공공기관 출처가 있는 후보만 남긴다 | `pipeline.PUBLIC_ORGS` |
| 5 | ① 증상 자리: 주호소 증상 순서대로, 아직 덮이지 않은 증상을 직접 덮는 원료 중 순서가 가장 앞선 것을 한 자리씩 고른다. TOP-10 밖이어도 올린다(`pipeline.symptom_slots`). ② 남은 자리는 순서가 남은 자리 수번째보다 앞서면 확정하고(`pipeline.split_fixed`), 그 순서와 기준이 모두 같은 동점 후보만 LLM이 고른다. 동점 후보 수가 남은 자리 수와 같으면 LLM은 고르지 않고 사유만 쓴다. 길항 쌍과 같은 원료군(`pipeline.SAME_FAMILY`: 인삼·홍삼, 글루코사민·NAG, EPA·DHA 계열. 약사 검토 전 초안)은 함께 고르지 않는다. LLM이 규칙을 어기면 버리고 순위대로 채운다. LLM은 앞 순위를 건너뛴 이유도 함께 적는다(`skipped`) | LLM, `pipeline.recommend` |

LLM은 OpenAI `gpt-6-luna`를 쓰고 키는 `../.env`에서 읽는다. 같은 요청은 `out/llm_cache`의 응답을 다시 써서 한 번만 과금된다.

알아둘 점은 다음과 같다.

- **관심사 연결은 나건강 표(기업 자료)가 원천이다.** 관심사만으로 올라온 후보는 4-3에서 그 원료의 식약처 기능성 문구를 출처로 삼는다. 관심사와 원료를 잇는 연결 자체에는 공공 출처가 없다.
- **원본 외 근거는 `origin = "추가 조사"`로 표시한다.** 원본 엑셀에 없고 국내 공공기관 자료에서 따로 찾은 근거(`load/refs/public_refs_kr.json`의 질환 → 증상·시너지·길항·생애주기 질환 통계, `load/refs/drug_nutrient_kr.json`의 복용약 → 영양소·허가사항 병용 주의)는 추천 로직에 쓰되, 관계·노드에 `origin`(생애주기 질환 통계는 `ref_origin`)을 붙여 화면에서 원본 근거와 구분한다.
- **복용약 근거는 식약처 의약품안전나라 허가사항 문장뿐이다.** `load/refs/drug_nutrient_kr.json`에 약 13개, `DEPLETES` 17건(A 7, B 10), 허가사항이 병용을 조심하라고 한 `INTERACTS_WITH` 5건이 있다. 성분마다 품목 1건만 확인했고 등급은 약사 검토 전 초안이다. 기획 시트 "드럭머거_21"의 고갈 영양소 열은 번역서가 출처라 쓰지 않는다. 스타틴 → 코엔자임Q10은 로바스타틴 허가사항에만 있는 문장을 계열에 적용한 B 등급이다.
- **약 인식은 이름·분류 글자에 거는 정규식이다.** 샘플처럼 분류가 적혀 있으면 잡히지만 제품명만 오는 처방 데이터에는 주성분 코드 대응표가 필요하다.
- **"직접 경로"는 원본 엑셀의 판정을 그대로 쓴다.** 기능성 → 기전 '일치'이고 기전 → 증상 '근거 있음'인 경로만 직접 경로다(`pipeline.is_direct`). 직접 경로로 덮는 증상 수가 순서의 첫 기준이라, 이 판정이 순위를 가장 크게 좌우한다.
- **생애주기 표의 질환 58행 중 46행은 심평원 통계로 연령·성별을 확인했다(`ref_*` 속성).** 나머지 12행은 표만 근거다. 질환 → 증상은 질병청 등 공공 출처로 확인한 126건을 쓴다.
- **경로는 기전을 거치며 넓게 퍼진다.** 증상 하나가 기전 여러 개로, 기전 하나가 기능성 여러 개로 이어져서 증상 하나에 후보가 수십~수백 개 나온다. "눈 건조함 → 여성호르몬 변화 → 뼈·칼슘 건강 → 칼슘"처럼 경로는 이어지지만 설명력이 약한 후보도 섞인다.
- **TOP-10은 같은 근거 경로를 가진 후보를 2개까지만 담는다.** 한 기능성의 원료가 목록을 채우지 않게 하려는 규칙이다(`pipeline.top_n`).
- **임신·수유·알레르기 여부는 입력 데이터에 없어 조건으로 넘기지 않는다.**

## 용어

| 용어 | 뜻 |
|---|---|
| 영양성분 | 비타민·미네랄 등 고시된 기본 영양소. "~에 필요" 표현 |
| 고시형 원료 | 식약처가 기준·규격을 고시해 누구나 쓸 수 있는 기능성 원료 |
| 개별인정형 원료 | 업체가 자료를 내서 식약처에 개별 인정받은 원료. 인정번호가 있고 일정 기간 독점 |
| 인정번호 | 개별인정형 원료 번호. 예: `제2025-64호` |
| h-code / s-code | 기획 시트의 검진 결과 코드(`h-3` = BMI 과체중) / 설문 응답 코드(`s-16-91`) |
| 드럭머거 | 약물이 체내 영양소를 고갈시키는 현상. 기획 시트 이름 |
| ATC 코드 | WHO 의약품 분류 코드. 예: 메트포르민 `A10BA02` |

# 건기식 원료 지식그래프 설계

LLM 건강 코치가 건강기능식품 원료를 추천하거나 설명할 때 근거로 쓰는 그래프 DB 설계다. 기준 자료는 기획 엑셀 `건기식원료_DB_261030_API정리.xlsx`(2025-10-30 버전, 시트 15개)이다.

## 1. 왜 그래프 DB인가

엑셀이 그리는 서비스는 단순 조회가 아니라 여러 단계를 따라가는 추천이다.

- 증상 → 기전 → 기능성 → 원료 (①증상기준 시트: "설명가능성을 확보하는 추천 엔진")
- 복용 약 → 고갈 영양소 → 증상 (드럭머거_21 시트)
- 검진·설문 조건 → 추천·제외 원료 (참고_결과&로직 시트)

이런 다단계 탐색과 "왜 이 원료를 추천했는지" 경로를 보여주는 기능에는 그래프가 맞다. 다만 역할을 나눈다.

| 저장소 | 담는 것 |
|---|---|
| **Neo4j** | 모든 사용자가 공유하는 지식 (원료, 증상, 약물 계열, 관계) |
| **RDB** | API 원본 스냅샷, 동기화 로그, 처방 약품 → 성분 매핑표, 추천 룰 정의 |
| **사용자 DB** | 개인 검진·설문·처방 데이터. **그래프에 넣지 않는다** |

## 2. 적재 파이프라인

```
식약처 API ─┐
크롤링 보완 ─┼→ 수집 스케줄러 → 원본 저장(RDB) → 정규화·검수 → Neo4j → 추천 룰 엔진
큐레이션 시트 ┘                                                      → LLM 답변
```

| 원천 | 서비스 / 시트 | 바뀌는 주기 (시트 기재) | 호출 주기 |
|---|---|---|---|
| 영양성분 | 2-1 시트 (고시 제2025-11호 원문) | 고정 | 고시 개정 시 수동 |
| 고시형 원료 | `I2710`, 공전 `I0960` | 연 1~2회 | 월 1회 |
| 개별인정형 원료 | `I-0050`, `I-0040` | 연 2회 또는 이벤트 | 주 1회 증분 + 월 1회 전체 ([SYNC.md](SYNC.md)) |
| 개별인정형 최신분 | 크롤링 (2-3 시트) | — | 주 1회. API에 없는 최신 인정번호만 보충 |
| 제품 | `I0030`, `C003` | 상시 | 일 1회 (야간) |
| 증상·기전·태그·약물·룰 | ①증상기준, 1-1, 원료별 기능성 태그, 증상 태그, 드럭머거_21, 참고_결과&로직 | — | 시트 수정 시 |

| `Condition` | `code` | `kind`(`exam`, `survey`, `population`, `disease`), `label`, `rule_group` | 참고_베어헬스몰 검진(h-code)·설문(s-code), 결과&로직 |

### 원료 유형은 보조 라벨로 나눈다

`(:Ingredient:Individual)`처럼 공통 라벨 `Ingredient`에 유형 라벨을 함께 붙인다.

- 탐색은 `(:Ingredient)` 하나로 유형 전체를 본다. 필요할 때만 `(:Ingredient:Individual)`로 좁힌다.
- 유형마다 라벨을 아예 따로 만들면 모든 쿼리·제약조건·인덱스가 두세 벌이 된다. Neo4j 5.x에서는 벡터 인덱스가 한 라벨에만 걸리므로 검색도 갈라진다. 여러 라벨에 걸친 벡터 인덱스는 2026.01부터 지원된다.

### 같은 물질은 Substance로 묶는다

같은 물질이 노드 여러 개로 나뉘는 경우가 있다.

- 업체별 개별인정: 이소말토올리고당 제2005-10호, 제2005-11호
- 고시형 전환: 개별인정형이 6년 이상, 품목제조보고 50건 이상이면 고시형 전환 검토 대상 (개요 시트)
- 사용자 표현과 공식 이름의 차이: "오메가3"와 "EPA 및 DHA 함유 유지"

각 원료는 그대로 두고 `(:Ingredient)-[:FORM_OF]->(:Substance)`로 묶는다. 이름 검색은 Substance의 별칭으로 찾은 뒤 원료로 내려간다.

### 관계

| 관계 | 의미 | 소유자 | 출처 |
|---|---|---|---|
| `(Symptom)-[:EXPLAINED_BY]->(Mechanism)` | 증상의 원인 가설 | 사람 | ①증상기준 |
| `(Mechanism)-[:SUPPORTED_BY]->(FunctionTag)` | 기전을 돕는 기능성 | 사람 | ①증상기준 |
| `(Ingredient)-[:HAS_FUNCTION {text}]->(FunctionTag)` | 원료의 기능성 | 사람 (검수) | 원료 기능성 문구 → 태그 |
| `(Mechanism)-[:REPLENISHED_BY]->(Ingredient)` | 결핍 기전을 채우는 영양소. 기능성 태그를 거치지 않는 직접 경로 | 사람 | 통합 엑셀 경로 시트 (결핍 기전 근거 상속) |
| `(Ingredient)-[:FORM_OF]->(Substance)` | 같은 물질 | 사람 | — |
| `(Ingredient:Individual)-[:CONVERTED_TO]->(Ingredient:Notice)` | 고시형 전환 이력 | 사람 | — |
| `(Drug)-[:IN_CLASS]->(Drug)` | 성분 → 계열 (메트포르민 → 혈당강하제) | 매핑 | ATC 코드 |
| `(Drug)-[:DEPLETES]->(Ingredient)` | 약이 고갈시키는 영양소 | 사람 | 드럭머거_21 |
| `(Drug)-[:MAY_CAUSE]->(Symptom)` | 약 부작용·고갈 증상 | 사람 | 드럭머거_21 |
| `(Ingredient)-[:INTERACTS_WITH {severity, note}]->(Drug)` | 병용 주의 | 사람 | 원료 주의사항 문구 |
| `(Condition)-[:RECOMMENDS {priority}]->(Ingredient)` | 조건별 추천 | 사람 | 결과&로직, 검진결과>추천 |
| `(Condition)-[:EXCLUDES {reason}]->(Ingredient)` | 조건별 제외 | 사람 | 원료 주의사항, 결과&로직 제외 옵션 |
| `(Product)-[:CONTAINS {amount, unit}]->(Ingredient)` | 제품 함량 | API | `I0030`, `C003` |
| `(Company)-[:MAKES]->(Product)` | 제조 | API | `I0030` |
| `(Company)-[:HOLDS_RECOGNITION]->(Ingredient)` | 개별인정 보유 | API | `I-0040` |

모든 관계에는 `source`(API 서비스 ID, 고시 번호, 시트명)와 `synced_at`을 남긴다. 사람이 만든 관계에는 `evidence`(`confirmed` 또는 `hypothesis`)도 남긴다.

### 룰은 그래프 밖에서 평가한다

결과&로직 시트의 규칙("다른 Option은 AND, 같은 Option 안은 OR, 제외 옵션")은 그래프 관계로 표현하기 어렵다. 룰은 RDB나 JSON에 두고 서버에서 평가한다. 평가 결과로 나온 활성 조건 코드(예: `h-3`, `s-16-91`)만 그래프의 `Condition` 노드와 매칭한다.

## 5. 질의 흐름

실행 파일: [`../cypher/30_queries.cypher`](../cypher/30_queries.cypher)

```
사용자 입력 (질문 · 검진 · 설문 · 처방)
 → 증상 정규화      symptom_fulltext, symptom_vector, name_lookup
 → 매칭 확실한가?   아니면 되묻기 (추천하지 않음)
 → 그래프 탐색      symptom_to_ingredient, condition_to_ingredient, drug_depletes

 → 근거 묶음        evidence_pack, products_for_ingredient
 → LLM 답변         근거만 보고 설명, 수치는 그대로 인용
```

### LLM의 역할

LLM은 그래프를 직접 조회하지 않는다. 서버가 위 쿼리를 정해진 순서로 실행하고 결과만 넘긴다.

| 하는 일 | 하지 않는 일 |
|---|---|
| 자유 문장을 증상 후보로 해석하도록 돕기 | 어떤 원료를 추천할지 결정 |
| 근거 묶음을 읽기 쉬운 답변으로 작성 | 섭취량 같은 수치 생성 |
| 되묻기 질문 작성 | Cypher 직접 작성 (text-to-Cypher) |

text-to-Cypher를 금지하는 이유: 쿼리가 틀리면 안전 필터를 건너뛰거나 엉뚱한 원료가 나올 수 있다. 질문 유형이 다양해지면 쿼리를 함수로 감싸 도구 호출(tool calling)로 노출한다. LLM은 함수와 파라미터만 고르게 한다.

## 6. 처방 데이터 연결

처방내역은 제품 단위(예: "다이아벡스정500mg", 보험코드, 처방일, 투약일수)로 들어온다. 드럭머거 시트와 원료 주의사항은 성분이나 계열 단위로 쓰여 있다. 그래서 중간에 매핑 단계를 둔다.

```
처방 제품 → (RDB 매핑표) 주성분 → Drug(level=ingredient) -[:IN_CLASS]-> Drug(level=class)
```

- **매핑표는 RDB에 둔다.** 보험코드 → 주성분 → ATC 코드. 수만 건 규모다. 후보 출처는 심평원 약가·주성분 자료, 식약처 의약품 허가정보 API, 심평원 ATC 매핑 목록이다. 정확한 서비스명과 필드는 아직 조사하지 않았다.
- **조회는 성분에서 계열까지 펼친다.** `safety_filter`와 `drug_depletes`는 `[:IN_CLASS*0..2]`로 계열까지 올라간다. 메트포르민 복용자에게 "혈당강하제 복용 시 주의" 원료가 걸리는 것은 테스트로 확인했다.
- **장기 복용을 구분한다.** 드럭머거 시트는 "약물 (장기)복용시" 기준이다. 처방일과 투약일수로 현재 복용과 장기 복용을 나눈다. 고갈 추천(`DEPLETES`)은 장기 복용일 때만, 안전 필터는 현재 복용이면 항상 적용한다.
- **설문 코드를 자동으로 켠다.** 결과&로직의 드럭머거 그룹은 설문 응답(예: `s-8-45` 당뇨약 복용)으로 걸린다. 처방이 있으면 같은 조건 코드를 켜서 설문 없이도 같은 룰이 돌게 한다.
- **매핑 안 된 약은 버리지 않는다.** 성분을 모르는 약이 있으면 안전 필터가 "문제없음"을 보장할 수 없다. 이때는 추천을 보수적으로 하고 "약사·의사 확인 권장" 문구를 붙인다.

## 7. 확인이 필요한 것

| 항목 | 현재 상태 | 영향 |
|---|---|---|
| 검진 전부 정상일 때 추천 | 엑셀에 로직 없음. 정상 구간은 추천 칸이 비어 있고 유지 문구만 있음 | 설문·증상으로만 추천하고, 그것도 없으면 유지 문구만 보여주는 안을 권장. 기획 결정 필요 |
| 빈혈 의심·혈색소 경계 (`h-55`, `h-49`, `h-56`, `h-50`) | 문구는 "철분 섭취 필요"인데 추천 원료 없음 | 누락인지 의도인지 확인 |
| 신장 이상 (`h-76`, `h-79`, `h-80`) | 추천 없음 | 의도라면 비워 두지 말고 `EXCLUDES`로 명시해야 안전 필터가 작동 |
| 배타 정보 시트 | 0행 | 원료 간 배타·금기 관계가 없음 |
| 기전 목록 | ①증상기준에 예시만 있음 | 증상 → 원료 설명 경로가 끊김 |
| 드럭머거 그룹 (결과&로직) | 상당수 "[작성요망]" | 처방 연동 효과가 제한됨 |
| 2-1 영양성분 세부 | 엽산·마그네슘·철·아연 등 제조기준 누락, 칼륨 일일섭취량 누락 | 고시 원문으로 보충 |
| `I-0050` 증분 조회 | 문서상 변경일자 조회만 지원 | 인증키로 호출해 확인 |
| 처방 데이터 형식 | 아직 정해지지 않음 (코드베이스에 처방 관련 테이블 없음) | 보험코드 유무에 따라 매핑 난이도가 달라짐 |
| 벡터 차원 | 1536으로 임시 지정 | 임베딩 모델을 정하면 `01_schema.cypher` 수정 |
| ID 규칙 | `NUT-`, `NTC-`, `IND-`, `SYM-`, `DRUG-`, `CLS-` 임시 | 정식 규칙 확정 |

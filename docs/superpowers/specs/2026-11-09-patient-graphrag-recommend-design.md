# 환자 정보 기반 GraphRAG 영양성분 추천 — 설계

- 작성일: 2026-11-09
- 상태: 검토 반영 초안 (사용자 승인 전)
- 이전 작업: 질의응답형 GraphRAG(`wcrag`)는 태스크와 맞지 않아 폐기. 로컬 브랜치 `archive/qa-graphrag`(커밋 `878f61a`)에 보존. main에서는 삭제했고, RAG DB(7689)도 비웠다.

## 1. 의도

BE가 환자 정보와 기본 데이터를 JSON으로 보낸다. 질문 문장은 없다. 이 서비스는 그 JSON만으로 **영양성분 3개를 우선순위대로** 추천한다. 그 과정에 GraphRAG를 쓴다. 그래프에서 환자에게 맞는 후보와 근거를 검색하고, LLM이 그 근거를 읽고 최종 3개와 순위를 정한다.

기존 규칙 엔진(`../graphdb/recommend`)도 같은 입력으로 3개를 고른다. 다만 엔진은 후보 생성기 8단계를 정해진 순서대로 돌며 앞에서부터 채운다. 그래서 다음을 판단하지 못한다.
- 여러 근거가 겹치는 성분(예: 증상과 검진 수치를 함께 커버)을 우대하는 것
- 3개가 한 가지 문제에 몰리지 않게 나누는 것
- 환자 상황 전체를 보고 순위를 정하는 것

이번 작업의 목적은 이 판단을 LLM이 하게 해서 **성분 선택 자체를 개선하는 것**이다(사용자 결정).

## 3. 목표 / 비목표 / 실패로 보는 것

**목표**
- 환자 JSON → 성분 3개(순위·근거·주의사항) JSON
- 금지 규칙 위반 0건을 코드로 보장한다. LLM의 판단에 맡기지 않는다.
- 같은 가상 환자셋에서 기존 엔진보다 근거 적합도·분산이 나은 3개를 고른다.

**비목표**
- 자연어 질의응답(이전 태스크)
- 용량 처방, 제품 추천
- BE 연동 API 서버(1단계에서는 함수와 CLI까지. 서버화는 나중 단계)
- 그래프 데이터·규칙 수정(`../graphdb`는 읽기만)

**실패로 보는 것(기능이 돌아가더라도)**
- 금지 성분이 한 번이라도 추천에 나오는 것
- LLM이 후보 목록에 없는 성분을 만들어 내는 것
- 근거가 그럴듯한 문장뿐이고 그래프 사실 ID로 추적되지 않는 것
- 엔진보다 못한 결과를 내면서 "LLM이 골랐다"는 이유만으로 채택하는 것

## 4. 제약

- API 과금 금지(개발·평가 중). LLM 판단·채점은 로그인된 Claude Code 세션으로 한다. 예외는 U8의 GPT 소량 재평가뿐이며, 실행 전에 사용자 승인을 받는다.
- `../graphdb` 코드·규칙·CSV 수정 금지. 개발 DB `supplement-neo4j-dev`(bolt 7688 / http 7475)는 읽기만. `supplement-neo4j`(7687) 접속 금지. 쓰기는 `supplement-neo4j-rag`(7689)만.
- `.env`, `.neo4j-*.env` 값은 읽지도 출력하지도 않는다. 가상환경은 `graphdb-rag/.venv`만.
- 개발·평가는 가상 환자만 쓴다. 평가 뒤 정답 수정 금지.
- 새 기능은 TDD(실패 테스트 → 구현 → 전체 통과).

## 5. 흐름

```
환자 JSON
 │
 ├─ ① 입력 검증·정규화(규칙)        나이·성별·질환·검진·약 → 그래프 키. 못 맞춘 것은 unmatched
 ├─ ② 주호소 정규화(LLM)            자유 문장 → 증상 분류 14종·증상 키워드, 위험 신호(red flag)
 │       └ 위험 신호면 추천 중단, 진료 권유(stopped)
 ├─ ③ 후보 수집(그래프)             모든 경로의 후보를 넓게 모은다(3개에서 멈추지 않음)
 │       각 후보 = 성분 + 근거 사실 목록(사실 ID, 경로 종류, 원문 출처)
 ├─ ④ 금지 판정(그래프 규칙)        avoid에 걸린 후보는 여기서 제거. LLM에게 보내지 않는다
 │       caution은 남기고 주의 문구를 붙인다
 ├─ ⑤ 최종 선택(LLM)               남은 후보와 근거 → 3개 + 순위 + 성분별 인용 사실 ID + 선택 이유
 ├─ ⑥ 검증(코드)                   후보 밖 성분, 금지 성분, 인용 없는 선택, 없는 사실 ID → 거부
 │       거부 시 1회 재시도 → 그래도 실패하면 엔진 순서(점수순)로 대체, status에 표시
 └─ 결과 JSON
```

## 6. 구성 요소

### ① 입력 정규화
엔진 `normalize.build_context`가 이미 질환·검진·약을 그래프 키(Condition 코드, Drug ID, Segment)로 바꾸고 `unmatched`를 만든다. **재사용한다.** 단, `build_context`는 `patient["sex"]`·`float(patient["age"])`를 그대로 읽으므로 앞에서 입력을 먼저 검증한다.

### ② 주호소 정규화(LLM)
- 기준표: `생애주기별 질환 및 증상_통합.xlsx`의 「증상별 정규화」 시트(14개 분류, 분류별 키워드).
- 출력 스키마: `{matches:[{category, symptoms[]}], unmatched[], red_flag, red_flag_reason}`. 기존 엔진 `llm.flatten`이 받는 형식과 같게 해서 엔진 후보 쿼리에 그대로 넣는다.
- 그래프의 `SymptomCategory` 14개와 엑셀 14개 분류는 이름이 같다(2026-11-09 확인). 구현에서는 대조 테스트로 이 일치를 고정한다.
- 같은 문장은 캐시해 같은 결과를 낸다.
- 입력에 `complaint`와 `symptoms`가 둘 다 있으면 **합집합**을 쓴다(내 판단). `symptoms`는 그래프 증상 이름과 대조해 그대로 넣고, `complaint`의 정규화 결과를 더한다. 엔진 `build_context`는 `normalized`가 들어오면 `patient["symptoms"]`를 버리므로, 합친 결과를 `normalized`로 넘긴다.
- 평가셋: `../graphdb/data/eval/complaint_testset.json`(472건, required/forbid/red_flag 정답 있음).
- 확인된 사실: 엔진 `llm.load_normalizer`가 import하는 `verify_symptom_normalization.py`가 `wellcheck/` 루트에 없다(`scripts/verify_normalization.py`만 있음). 엔진의 `--llm` 경로는 지금 깨져 있을 수 있다. 그래서 정규화 프롬프트는 새로 쓴다.

### ③ 후보 수집(그래프)
엔진 `candidates.py`의 8개 생성기(증상 직접, 복용약 고갈+증상, 증상 분류→기능, 검진 규칙, 질환 규칙, 복용약 고갈, 경계 수치, 성별·연령대 관심사)와 **같은 매칭 조건**으로 후보 풀을 만든다. 모든 생성기를 실행하고, 엔진처럼 3개를 채우면 멈추지 않는다.
- **쿼리는 새 패키지에 새로 쓴다(내 판단).** 엔진 쿼리는 근거를 `collect(... + ' → ' + ...)` 문자열로 합쳐서 돌려주고 노드·관계 ID를 주지 않는다. 그래서 그대로 재사용하면 사실 ID를 만들 수 없다. 새 쿼리는 같은 WHERE 조건에 경로의 노드 ID와 관계 속성을 돌려준다.
- **엔진과 어긋나는 것을 막는 장치**: 평가 환자셋 전체에서 "새 후보 풀의 성분 ID ⊇ 엔진 생성기가 낸 성분 ID"인지 확인하는 동등성 테스트를 둔다. 엔진은 `select()` 전 단계까지 import해서 비교한다.
- 금기 규칙(④)은 엔진 `safety.check`를 import해서 그대로 쓴다. 금기의 단일 원천은 엔진이다.
- **근거 사실 1개 = 경로 1개(내 판단).** 고갈+증상(MAY_CAUSE+DEPLETES), 분류→기능(INCLUDES·ADDRESSED_BY·HAS_FUNCTION), 관심사(HAS_INTEREST+RECOMMENDS)처럼 여러 관계로 된 경로도 하나의 사실로 본다. 경로 일부만 인용하는 일이 없게 하기 위해서다. 사실 ID는 `경로종류:노드ID1>노드ID2>…` 형식이다. 사람이 읽는 문장과 `source`(RELIEVED_BY처럼 원문 출처 속성이 있을 때만, 없으면 `null`이고 경로 종류로 출처를 표시)를 함께 가진다.
- 같은 성분이 여러 경로에서 나오면 근거를 합친다(엔진의 묶음·구성 성분 처리 `group_of`·`overlaps` 규칙 유지).
- 후보마다 규칙 점수(엔진 단계 순위 기반)를 붙인다. LLM 입력 정렬과 ⑥의 대체 경로에 쓴다.
- 후보 풀 상한: 규칙 점수 상위 N개(기본 20, 내 판단). LLM 입력 크기를 제한하기 위해서다.

### ④ 금지 판정(그래프 규칙)
엔진 `safety.check`를 **그대로 재사용한다**(금기 규칙의 단일 원천).
- `Condition -[:EXCLUDES]-> Ingredient`: 환자 질환·검진 조건 코드. severity `avoid`면 제외, `caution`이면 주의. `scope=product`는 주의.
- `Ingredient -[:INTERACTS_WITH]-> Drug`: severity `avoid`면 제외. 그 외(`consult` 등)는 주의.
- 주의 등급 처리(U9)는 설정값 `CAUTION_POLICY = "keep" | "exclude"`로 둔다. 기본값은 `keep`이다. `exclude`로 바꾸면 `must_not` 계산도 같이 바뀐다.
- 드럭머거(U3): `DEPLETES`는 ③에서 후보 사유가 된다. 그 성분이 ④에서 avoid에 걸리면 제외된다. 예: 80세 픽스처의 마그네슘은 GFR·혈압약 때문에 제외된다.
- 제외된 성분은 LLM 입력에 넣지 않는다. 결과 `excluded`에만 남긴다.

### ⑤ 최종 선택(LLM)
- 입력: 환자 요약(성별·연령대·정규화된 증상·질환·검진 이상·복용약 계열; 이름 같은 식별자 없음), 후보 목록(성분 ID·이름·근거 사실 ID와 문장·주의 문구·규칙 점수).
- 지시: 후보 목록 안에서만 3개를 고른다. 성분마다 근거 사실 ID를 1개 이상 인용한다. 우선순위 판단 기준은 근거의 강도(확인된 고갈·직접 완화 > 분류 기능 > 관심사)와 여러 문제를 함께 커버하는지, 3개가 서로 다른 문제를 나누는지, 주의 문구가 있는 성분은 대안이 있으면 뒤로 미루는지다.
- 출력 스키마: `{picks:[{ingredient_id, rank, fact_ids[], reason}]}`. 구조화 출력을 쓴다.
- 건강기능식품 표현 규칙: 치료·완치·예방 단정, 용량, 복약 변경 권유 금지. `reason` 문장 검사에 엔진 `llm.FORBIDDEN` 패턴을 준용한다.

### ⑥ 검증(코드)
다음 중 하나라도 걸리면 그 응답은 거부한다.
- 후보 풀 밖 성분, 또는 ④에서 제외된 성분
- `fact_ids`가 비었거나, 그 성분의 근거 목록에 없는 사실 ID
- 순위 중복·누락, 같은 성분 중복, 묶음과 그 구성 성분 동시 선택
- `reason`에 금지 표현

거부되면 사유를 붙여 1회 재시도한다. 그래도 실패하면 규칙 점수 순으로 3개를 채우고 `selector="fallback_rules"`로 표시한다. 후보가 3개 미만이면 LLM을 부르지 않고 있는 만큼만 내고 `partial`로 표시한다.

## 7. LLM 호출과 과금 원칙

- LLM 호출은 `LLMClient` 인터페이스 하나로 감싼다(정규화, 선택). 구현체는 셋이다.
  - `FakeLLM`: 테스트용 고정 응답.
  - `SessionLLM`(개발·평가용): 요청 프롬프트의 해시를 키로 응답 파일을 읽는다. 외부 API 호출 0.
  - `OpenAILLM`(운영용, U8): GPT 구조화 출력. 모델명은 설정값이다. 키는 `wellcheck/.env`(엔진과 같은 곳)에서 코드가 읽는다.
- **세션 응답이 없을 때(내 판단)**: 평가는 2단계로 돈다. ① `export`: 모든 요청 프롬프트를 `out/session/requests/*.json`로 내보낸다. ② Claude Code 세션이 각 요청에 답해 `out/session/responses/*.json`에 쓴다. ③ `run`: 응답을 읽어 결과를 만든다. `SessionLLM`이 응답을 찾지 못하면 **에러**를 낸다. 조용히 규칙 대체로 넘어가면 평가가 오염되기 때문이다. ⑥의 `fallback_rules`는 "LLM이 응답했지만 검증에 실패한 경우"에만 쓴다.
- 세션은 정규화 472건과 환자 30명의 선택을 답한다(U10). 세션이 답하는 프롬프트는 운영 GPT에 보낼 프롬프트와 **같은 문자열**이어야 한다(U8 재평가와 비교할 수 있게).
- 테스트 중 외부 호출은 예외로 막는다.

## 8. 평가

**환자셋**: 가상 환자 30명 내외(내 판단). 구성:
- 기존 픽스처(80세 남성)
- archive 브랜치 `eval/questions.json`의 환자 문항 14건(P-01~P-15, P-13 제외)을 입력 JSON으로 옮긴 것
- 금지 규칙을 일부러 건드리는 사례(와파린+코엔자임Q10, 저GFR+마그네슘, 메트포르민+B12 고갈 등)
- 주호소만 있는 사례, 약만 있는 사례, 정보가 거의 없는 사례

환자마다 `must_not`(금지 성분, 그래프 규칙에서 기계적으로 계산)을 둔다.

**게이트 G1(필수, 기계 채점)**: 전 환자에서 금지 성분 추천 0건, 근거 없는 추천 0건, 후보 밖 성분 0건, 스키마 오류 0건.

**비교 G2(세션 채점)**: 같은 환자에 대해 엔진 결과와 새 결과를 나란히 놓는다. **공정한 비교를 위해 엔진에도 ②의 정규화 결과를 `build_context(normalized=...)`로 똑같이 넣는다(내 판단).** 그래야 정규화가 있고 없고의 차이가 아니라 선택 단계의 차이만 잰다. Claude Code 세션이 어느 쪽이 나은지 블라인드로(A/B 무작위) 채점한다. 기준은 근거 적합도, 환자 문제 커버리지, 3개의 분산, 주의 성분 회피다. 통과 기준(내 판단, 조정 가능): 새 결과가 엔진보다 나음 또는 동등인 비율 ≥ 80%, 엔진보다 확실히 못함 0건.

**사람 확인**: 엔진과 결과가 다른 환자를 엑셀(`out/eval/*.xlsx`)로 뽑는다. 환자 요약, 엔진 3개, 새 3개, 근거, 채점 이유를 담는다.

**정규화 평가**: `complaint_testset.json` 472건 전부로 required 충족률, forbid 위반, red_flag 재현율을 잰다.

**운영 모델 재평가 G3(과금, 승인 필요)**: 1단계 끝에 환자 30명을 GPT로 다시 돌린다. G1을 그대로 통과해야 하고, 세션 결과와 3개가 얼마나 일치하는지 보고한다. 실행 전에 예상 호출 수와 비용을 보여 주고 승인을 받는다.

## 9. 코드 배치(내 판단)

```
graphdb-rag/
  rxrag/                  # 새 패키지(이름은 임시)
    contract.py           # 입력 검증, 출력 스키마
    legacy.py             # ../graphdb/recommend 읽기 전용 어댑터(build_context, 생성기 쿼리, safety.check)
    graph.py              # Neo4j 읽기 연결(dev 7688 읽기 전용)
    normalize.py          # ② 주호소 정규화
    candidates.py         # ③ 후보 풀 + 근거 사실 ID
    select.py             # ⑤ LLM 선택 프롬프트·스키마
    verify.py             # ⑥ 검증·대체
    recommend.py          # 진입점 recommend(patient) -> dict
    llm.py                # LLMClient, 캐시·세션 응답·가짜 구현
    cli.py
  eval/                   # 환자셋, must_not, 채점 스크립트
  tests/
```

그래프는 dev DB를 읽기로만 쓴다. 이번 방식(U1)은 임베딩 검색이 필요 없어서 7689에 복제할 이유가 없다. 7689는 비워 둔 채로 두고, 나중에 임베딩이 필요해지면 그때 쓴다.

**접속(내 판단)**: 엔진 `safety.check`와 동등성 비교가 엔진의 `db.run` 인터페이스(HTTP 클라이언트)를 쓰므로 같은 클라이언트를 쓴다. 접속 정보는 엔진과 같은 `graphdb/.neo4j-dev.env`에서 코드가 읽는다. "env 값을 읽지 않는다"는 에이전트가 값을 보거나 출력하지 않는다는 규칙이다. 단 엔진 `db.connect()`처럼 파일이 없을 때 `localhost:7474`(접속 금지 DB의 HTTP 포트)로 떨어지는 기본값은 쓰지 않는다. 우리 `graph.py`는 URL이 없거나 포트가 7475가 아니면 즉시 에러를 낸다. 쓰기 쿼리를 보내지 않도록 읽기 전용 래퍼(`CREATE|MERGE|DELETE|SET|REMOVE|DROP` 거부)로 감싼다.
